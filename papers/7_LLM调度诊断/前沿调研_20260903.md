# 方向7 前沿调研：LLM 诊断的工作流范式与构造验证（2026-09-03）

> 三路并行调研：① LLM×调度/组合优化 ② LLM×根因诊断(AIOps/工业) ③ LLM×MAPF/仿真验证。
> 确证等级：【摘】=读过 arXiv 摘要/原文；【题】=仅搜索标题/片段，写入 related work 前需读原文。

## 一、LLM 在调度领域的一般工作流（5 种模式）

| 模式 | 代表 | LLM 角色 | 验证方式 |
|---|---|---|---|
| 生成-执行-进化 | FunSearch【题】/EoH【摘】/ReEvo【摘】/LLaMEA【题】/HeurAgenix【题】 | 生成启发式代码，引擎当裁判 | 程序执行+适应度反馈循环 |
| 翻译-形式求解 | LLM+P【摘】/Logic-LM【摘】/Chain-of-Experts【摘】 | NL→PDDL/数学模型→求解器 | 求解器结果背书 |
| 微调直接求解 | Starjob【摘】 | SFT 后端到端出 JSSP 解 | 仅小规模实例可行 |
| 在线轨迹反思 | ReflecSched【摘】(2508.01724) | 读仿真轨迹提炼"策略经验"文本，服务**在线**决策 | GEN-Bench 在线评测 |
| 基准评测 | CO-Bench【摘】(AAAI'26)/DynaSchedBench【题】(ICML'26) | LLM 为被测对象 | 执行对比专家算法 |

MAPF 侧：LLM 直接规划已被证伪（Why Solving MAPF with LLM is Unsolvable, 2401.03630【摘】）；
主流是翻译-求解（LLM+P 系）或混合（LLM-NAR【摘】）。LLM-Modulo【摘】(ICML'24) 定调"生成-验证闭环"。

**结论：调度领域 LLM 的角色全部是"前馈"（生成/翻译/选择/在线反思），没有任何"事后诊断"工作。空缺真实存在。**

## 二、LLM 根因诊断（RCA）领域的一般工作流（3 种模式）

| 模式 | 代表 | 说明 |
|---|---|---|
| 单轮打包 | RCACopilot【摘】(2305.15778)、OpenRCA【题】(ICLR'25) | 按告警类型聚合诊断信息，LLM 一次预测根因 |
| **Agentic 多轮工具调用** | RCAgent【题】、Cloud-OpsBench【摘】(2603.00468)、ITBench【摘】(ICML'25) | 告警→假设→工具取证→迭代→结构化诊断，2025-26 基准的主流评测对象 |
| 多代理交叉验证 | mABC【摘】(EMNLP'24) | 7 agent + 投票抑制幻觉 |

关键事实：
- **Ground truth 主流 = 受控故障注入**（ChaosBlade/K8s 混沌工程），与我们场景库做法一致。
- Cloud-OpsBench 的场景构建 = **Generator→Executor→Verifier 自动闭环 + 状态快照冻结**（每例冻结为确定性数字孪生，预计算 ~487 次工具响应保证可复现）——可直接借鉴为场景库自动化方案。
- 指标两层：**结果**（A@1/A@3、resolution rate）+ **过程**（MTTI、工具覆盖率、无效动作率）。
- 2026 基准明确批评单轮打包为"passive classification"，主张评 **active reasoning**。

## 三、反事实验证机制的先例与规范

- **最邻近先例**：arXiv 2608.09343【摘】(2026)——LLM 重放最差 trace→瓶颈诊断→改码→**100 个 matched seeds 重仿真**，仅保留有测量增益的候选（但它是优化启发式，非诊断层）；arXiv 2505.02076【摘】——数字孪生对 LLM 纠正动作做实施前验证（流程工业）。
- **同 seed 配对 = 仿真领域 Common Random Numbers (CRN)**，标准方差缩减技术；规范做法是同 seed 配对差 + ≥30 seeds 显著性检验（配对 t/Wilcoxon），随机流需同步（同一随机数用于同一目的）。单 seed 只作案例展示。
- **"重仿真 + ΔKPI 量化评分"在 RCA 文献中罕见**——领域组合仍新，但必须引用上述两篇划界。
- **LLM 反事实推理系统性弱**（可检验假设）：CounterBench【摘】(2502.11008) 多数模型≈随机；Executable Counterfactuals【摘】(2510.01539) 从 interventional 到 counterfactual 掉 25-40%，且现有基准普遍跳过 abduction 步骤导致高估。→ "无事件纯统计推断" hard 案例恰需 abduction，预期 LLM 系统性弱，与规则基线/事件可见案例形成分层对照。

## 四、构造验证结论（三件套逐项）

| 构件 | 验证结果 |
|---|---|
| 场景库（注入出题） | ✅ 方法论与 AIOps 混沌工程、DynaSchedBench planted faults 完全对齐，是标准做法；建议升级为 Cloud-OpsBench 式 Generator→Executor→Verifier 自动闭环 |
| 案例库（打包考卷） | ⚠️ 单轮打包本身是有效消融，但 2026 基准风向是 agentic；建议案例数据同时支撑两种观测方式 |
| 干预桥（ΔKPI 判卷） | ✅ 最有区分度的构件：RCA 文献罕见重仿真量化验证，无直接撞车；需升级为 CRN 多 seed 规范 |
| 撞车检查 | ✅ 三域均未发现"LLM 事后诊断调度系统+反事实重仿真验证干预"先例；最近邻 ReflecSched（在线）、DynaSchedBench（诊断对象是 LLM agent 而非系统）、2608.09343（优化启发式）、2505.02076（流程工业 DT） |

## 五、构造需要修订的五点

1. **观测方式双层化**：主系统做 agentic 版（引擎即工具：查 KPI / 查事件 / 提交干预→触发反事实），单轮打包降为消融臂——反而能支撑"结构化运行档案已足够强"或"主动取证必要" whichever 结果。案例库底层同一份数据，两种视图。
2. **反事实验证协议升级**：同 seed 配对差（CRN）+ 30-100 seeds 显著性检验；论文明确随机流同步。同 seed 配对本身视为应做而非贡献，贡献落在诊断层设计与 hard 案例发现。
3. **指标补过程维度**：无效干预率（干预不可执行/词表外）、（agentic 版）MTTI、工具覆盖率、轨迹与专家路径对齐；结果维度保持 A@1/归因准确率。
4. **忠实度做 statement 级**：借鉴 "Correctness is not Faithfulness in RAG"（ACM'25）——引用指向对 ≠ 论断被支持；程序化回查 + LLM judge 双轨评分。
5. **干预建议加一轮 ReEvo 式反思精化**（best-so-far 反馈重写干预），否则被审稿人视为弱于进化类基线的单轮系统。

## 七、可检验假设（预注册式）

- H1: easy 案例（事件可见）LLM≈规则基线；hard 案例（无事件纯统计推断/abduction）LLM 与基线都掉，但接地约束下的 LLM 掉得少（若掉得多，忠实度/可验证性成为唯一卖点）。
- H2: 接地约束 A/B——有约束时忠实度显著升、定位/归因不降。
- H3: 反事实 ΔKPI 评分下，LLM 干预成功率 > 规则基线查表干预（或诚实呈现无差异，重心移向评测框架本身）。
- H4: 信息预算曲线（4k/8k/16k token 档案）呈现 observability paradox 或正常增益，任一结果都可写。
