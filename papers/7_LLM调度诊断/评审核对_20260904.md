## 二、采纳（写入 v2.1 改稿清单）

1. **第一主线换轴**：从"LLM 做诊断"换成"可仿真验证的解释"——
   `Diagnosis → Evidence grounding → Executable intervention → ΔKPI`；
   英文标题采纳：*Can LLMs Explain Scheduling Failures? Engine-Grounded Diagnosis
   with Executable Counterfactual Verification*。
2. **taxonomy 二分**（评审最锐利的一点）：`Injected causal failures`
   （do(F=1) vs do(F=0)，CRN 下是干净的干预效应）与
   `Emergent systemic failures`（签名定义的 phenomenological diagnosis，
   无 do() 真值）分列——比我们方法论 §6 的"标签不对称"更精确。
3. **Diagnostic Utility 形式化**：`Utility = E[ΔKPI(π(e))]`，
   diagnosis→treatment→outcome 医学类比；干预从附属指标升级为并列主张。
4. **RQ1 提法**："Does an LLM diagnose scheduling failures, or merely read
   explicit fault traces?"——easy/hard 孪生正是为此设计。
5. **procedural benchmark 定位**：不再强调"104"，强调生成器 coverage 与
   held-out 泛化；扩网格至 500-2000 场景（生成器现成，服务器跑）。
6. **AIOps 差异化扩写十倍**：AIOps 是 fault→service propagation→incident
   （原因对应显式故障事件）；我们是 machine/AGV/scheduler→resource interaction→
   **emergent scheduling pathology**→makespan（原因可以没有任何显式事件，
   所有组件各自正常但组合死亡）。这必须成为引言的主段落。
7. **姊妹篇统一叙事**：Simulator-as-Oracle for Decision（决策篇）/
   Simulator-as-Verifier for Explanation（本篇）。
