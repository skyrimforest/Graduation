# SkyOrch(原 LLM4Schedule):背景介绍与科研故事构思

> **改名说明(2026-08-27)**:原名 LLM4Schedule 已撞车——CityU/HKU 系 2026 年 SSRN 论文 "Can Large Language Models Improve Scheduling Policies?" 的方法名即 LLM4Schedule(定位同为"LLM 不直接调度、在仿真反馈下优化调度策略",见 [ResearchGate](https://www.researchgate.net/publication/410901123))。本项目更名为 **SkyOrch**(延续 SkyEngine/SkyCausal 家族,强调 solver orchestration)。
>
> 定位一句话:LLM 作为在线 Coordinator,在 FJSP-MAPF 联合调度中做**算子组合选取 + 参数配置**,以多层耦合执行反馈为选择依据。
>
> 与姊妹篇的边界(已钉死):
> - **SkyOrch = 在线、组合已有算子**(消费专家池,读取专家能力卡做组合推理);
> - **LLM4Envolve = 离线、进化生成新算子**(生产专家池,LLM 写 dispatching rule 代码,Eureka/FunSearch 一脉)。
> - 两篇互相引用、共享 SkyEngine 环境与专家池基建,但方法与贡献不重叠。概念交叠处的边界表述:SkyOrch **读卡组合已有专家**,LLM4Envolve **写卡生产新专家**。

---

## 一、问题背景:为什么要 LLM 做算子组合选取

### 1. FJSP-MAPF 联合调度的组合爆炸

柔性制造系统的调度由三层算子堆叠而成:

| 层 | 决策内容 | 可选算子(专家池) |
|---|---|---|
| FJSP 层 | 工件→机器、工序排序 | 各类 PDR、启发式、精确求解器 |
| Assigner 层 | 路由任务→AGV | 就近分配、负载均衡、学习式分配 |
| MAPF 层 | AGV 无碰撞路径 | CBS 系、优先级规划、规则式路由 |

三层算子的最优组合**随系统状态变化**:同一组算子在"多 job 长流程"状态下最优,在"拥堵聚集"状态下可能显著劣化。固定组合必然次优,而组合空间是三层笛卡尔积,穷举不可行——这正是 algorithm selection / hyper-heuristic 的经典场景,但联合调度场景下此前无人用 LLM 做。

### 2. LLM 直接当调度器已被证明是死路

ReflecSched(arXiv:2508.01724, 2025)系统论证了 LLM 直接输出调度决策的三个失效模式,可直接引用为我们设计选择的论据:

1. **长上下文悖论**:prompt 中 >70% 的静态状态数据被忽略,删除后性能几乎不变;
2. **启发式闲置**:即使明确指示 LLM 遵循 PDR,它也不遵守;
3. **短视贪婪**:局部好的选择造成下游瓶颈。

结论:LLM 的价值不在"执行"而在"统筹"——这恰好回到 Coordinator/meta-controller 的位置。

### 3. 我们的差异化基建:多层耦合执行反馈

需要先钉死术语,避免自己搞混(也与姊妹篇边界一致):

- **"在线"= episode 内 in-the-loop**:仿真回合进行中,LLM 在决策/切换点介入(LLM4Schedule 即此);
- **"离线"= episode 外**:部署前用 LLM 生成规则/代码(LLM4Envolve 即此);
- 我们与竞品**同为离线仿真实验**,"在线"指的都不是真实工厂部署,不作为卖点表述。

真正的差异在于**反馈信号的来源和内容**:

| 范式 | 反馈给 LLM 的信号 |
|---|---|
| 解耦两阶段 | 无反馈(调度定完才执行,单向) |
| ReflecSched | lookahead rollout 的假想轨迹摘要(且假设 lookahead 期间无新事件) |
| LAOS / LLM4EO | EA 迭代的单目标适应度增量 |
| **SkyEngine(本文)** | **多层联合执行的耦合反馈**:每个调度动作立即在共仿真中执行(AGV 真实移动、阻塞、绕行),执行结果重塑机器可用性与后续决策点;17 项指标覆盖 FJSP 与 MAPF 两侧 |

即:LLM 能从反馈中读到"换了 MAPF 求解器后拥堵下降、但机器空闲上升"这类**跨层联动信息**,这是单层选择器(EA 内选算子、单层 rollout)在结构上无法获得的,也是本文的差异化基建。

## 二、前沿进展综述(调研于 2026-08)

按 LLM 介入环节分三类:

### 类别 A:LLM 做策略/算子选择(与本文最贴身)

| 工作 | 发表 | 核心机制 | 与本文的差异 |
|---|---|---|---|
| **ReflecSched** ([arXiv:2508.01724](https://arxiv.org/html/2508.01724v1)) | 2025 | 层级化 Simulate-Reflect-Refine:LLM 对比好/差 rollout 轨迹,蒸馏自然语言 Strategic Experience 注入决策 prompt | 单层 DFJSP,无 MAPF;输出自然语言经验(不可验证)而非离散算子组合;未与 DRL 基线对比 |
| **LAOS** ([ACM](https://dl.acm.org/doi/10.1145/3712256.3726450)) | GECCO'25 | LLM-driven Adaptive Operator Selection:在进化算法迭代循环内部,LLM 依据适应度反馈在线选择**进化算子**(crossover/mutation/destroy-repair) | 被选的是 EA 算子而非调度系统算子;反馈信号是单目标适应度增量,不携带调度-搬运耦合信息 |
| **LLM4EO** ([arXiv:2511.16485](https://arxiv.org/pdf/2511.16485)) | 2025 | 面向 FJSP 的 LLM 在线算子设计,增强 EA | **问题域重合的最近竞品**;但只有 FJSP 单层,算子是 EA 算子,反馈是适应度改进量,无联合执行反馈 |
| **LLM-assisted ALNS** ([FEM](https://journal.hep.com.cn/fem/EN/10.1007/s42524-026-5124-4)) | 2026 | LLM 选 destroy/repair 算子 | ALNS 骨架,单问题单层 |

### 类别 B:LLM 做参数/配置调优

- **LLaMEA-HPO** ([arXiv:2410.16309](https://arxiv.org/html/2410.16309v1), van Stein et al.):核心论点"**算法结构搜索与参数调优应分离**"——LLM 负责结构设计,专用 HPO 负责参数。对我们的启示:LLM4Schedule 的输出空间应显式分成"离散算子组合(结构)+ 连续参数(配置)"两部分,后者可考虑 LLM 粗调 + 局部精调的混合。
- **Tuning Metaheuristics with LLMs** ([Neurocomputing](https://www.sciencedirect.com/science/article/abs/pii/S0925231226003735)):直接验证 LLM 调元启发式参数的可行性。
- **LLMHHEA** ([Sci. Rep.](https://www.nature.com/articles/s41598-026-52801-3)):LLM 辅助超启发式进化框架。

### 类别 C:直接竞品与临近工作(2026-08 外部 review 补充,引用前需逐条核实原文)

- **LLM4Schedule(撞名,SSRN)**:[Can LLMs Improve Scheduling Policies?](https://www.researchgate.net/publication/410901123_Can_Large_Language_Models_Improve_Scheduling_Policies_Evidence_from_Queueing_Networks_Job_Scheduling_and_Ride-Hailing_Dispatch) 两阶段:LLM 生成可执行 scoring policy 模板 + rollout 反馈迭代调参,部署时无需 LLM。与我们同区间(仿真反馈 + LLM 不直接调度),差异:单层调度策略模板优化 vs 三层异构求解器栈编排。
- **LLMOA**(ScienceDirect 2024):LLM(Gemini)作 hyper-heuristic 高层,从十个低层启发式中构造算子序列——"LLM 选低层算子"这个抽象本身不新,我们的差异必须来自算子的语义层次、物理耦合与反馈结构。
- **动态 dispatching rule 选择**(CIE 2025):state→rule 的 SL/RL 切换,tardiness 比最佳固定规则提升 >10%;并发现 **periodic 选择比逐决策点切换更 robust**——直接支持我们的慢时间尺度设计,使其从工程妥协升格为 design principle。
- **Digital Twin + LRM + Bandit**(JMS 2026):孪生造扰动环境,LRM 生成结构化规则,bandit 筛选演化。结构与我们最接近的正面对手,比 LLM4EO 更值得对比。
- **LLM embedding 做 algorithm selection**(COR 2026):frozen LLM 表示已能匹配手工特征做算子选择——reviewer 会问"你的 7B 是不是就是个很贵的 state classifier",必须用开放集实验回应。
- **LLM × MAPF**:已有 [LLM-NAR](https://arxiv.org/abs/2508.17971)(神经算法推理器+LLM)、[Offline RL + LLM for MAPF](https://arxiv.org/abs/2509.22130)——**"LLM×MAPF 基本为空"不成立,已删除**。正确表述:已有工作聚焦用 LLM 做路径求解本身,我们把 MAPF 求解器作为高层 orchestration 的专家之一。
- **FJSP+AGV+路径联合框架**已出现(JSP-MAPF 统一框架、异构 AGV 分配+MAPF 耦合,2025-26)——场景本身不能声称空白,但这对我们是好事:证明该问题正在成为 emerging research problem,我们做的是下一步(编排多个异构求解器,而非设计单一 integrated 算法)。

### 综述与基准

- **LLM-Assisted Combinatorial Optimization 综述** ([SciOpen](https://www.sciopen.com/article/10.23919/CSMS.2026.0007)):按数学规划/启发式/端到端三分,明确提及 online operator selection 方向。
- **LLM4CO 综述** ([ACM CSur](https://dl.acm.org/doi/10.1145/3801961)):指出 LLM 探索算法选择空间可定位现有求解器的失效区。
- **awesome-fm4co** ([GitHub](https://github.com/ai4co/awesome-fm4co)):持续更新的文献清单。
- (类别 D:LLM 离线生成启发式代码 —— Eureka/FunSearch 脉络,归 LLM4Envolve,此处不展开。)

### 空白点结论(v2,吸收外部 review 后修正)

1. **多层耦合场景的 LLM 编排无人做**——但单层/EA 内的 LLM 算子选择已有(LAOS、LLMOA、LLM4EO),"LLM 选算子"这一抽象本身不构成 novelty,差异必须来自三层异构物理耦合与跨层反馈结构;
2. **反馈信号不携带跨层耦合信息**——现有均为单层 rollout 假想代价或适应度增量;
3. **现有工作的输出空间偏软**(自然语言经验,不可验证、不可复现);
4. **开放集编排无人做**——unseen expert(训练时未见、测试时给能力卡)、regime shift、objective shift 下的组合泛化,是 MLP/bandit 类 selector 结构性做不到、而语言条件化 LLM 天然适配的问题——**这是"为什么必须 LLM"的核心论证位置**。
5. ~~LLM × MAPF 基本为空~~ **已撤回**(存在 LLM-NAR 等工作,见类别 C)。

## 三、科研故事构思

### 故事线(初版)

```
现象:三层算子组合无单一最优,固定组合随状态漂移显著劣化
  ↓ 分析:算子组合的优劣取决于耦合状态(距离/时序/拥堵三类耦合损失),
          需要理解"状态语义"才能选对组合
  ↓ 现有方案的缺口:bandit 类自适应选择无语义推理;
          LLM 直接调度不可行(ReflecSched 三失效);
          现有 LLM 选择器只覆盖单层、无闭环反馈
  ↓ 方法:LLM4Schedule —— LLM 作为闭环 Coordinator,
          慢时间尺度输出三层算子组合 + 参数,以 SkyEngine 17 项指标为反馈
  ↓ 验证:打赢固定组合 / 随机组合 / bandit / 单层 LLM 选择器 / ReflecSched 式方案
```

### 核心设计选择(需要想清楚的)

1. **输出空间**:结构(离散算子组合,合法集合内约束解码)与参数(数值,LLM 粗选 + 可选局部精调)分离——借鉴 LLaMEA-HPO 的分离原则。
2. **介入时机**:慢时间尺度(episode 级 / 扰动事件级),高频决策留给底层算子——规避延迟问题,也让"LLM 做的是统筹而非执行"的叙事自洽。
3. **反馈机制**:闭环指标 → LLM 上下文(结构化摘要,防长上下文悖论)→ 下一次选择。可设计经验积累机制(跨 episode 的选择-结果记忆)。
4. **与 SkyCausal v3 的关系**:归档的旧稿(solver-portfolio meta-scheduling,无 LLM)是本文的直接前身——它证明了"组合元调度"这个问题设定成立,本文升级为"LLM 驱动的组合元调度"。旧稿的非 LLM 组合器可直接用作最强基线之一。

### 必须提前防守的审稿质疑

| 质疑 | 防守 |
|---|---|
| "LLM 比 bandit 强在哪?" | 设计**凸显状态语义的实验**:按三类耦合损失构造分状态评测(如拥堵聚集型状态需换 MAPF 求解器),展示 bandit 在状态语义切换处反应慢/错误,LLM 能从反馈中推理出切换理由;而非在均匀随机场景比总比分 |
| "是不是 prompt engineering 的功劳?" | 输出离散可验证、多模型一致性测试(GPT/Qwen/DeepSeek 跨模型)、消融反馈机制 |
| "延迟能上线吗?" | 慢时间尺度介入的延迟预算分析;LLM 调用频率与性能的 trade-off 曲线 |
| "和 LLM4EO 的区别?" | LLM4EO 在 EA 循环内选进化算子、反馈为适应度增量、仅 FJSP 单层;本文选调度-分配-路由三层算子,反馈为联合执行的多指标耦合信号,组合错误会跨层放大 |

### Baseline 清单(初步)

1. 固定最优单组合(oracle-per-dataset,用 SkyCausal v3 的组合器搜索得到);
2. 随机组合 / 轮转;
3. 无 LLM 自适应选择:Thompson sampling、UCB、EXP4;
4. SkyCausal v3 的非 LLM 元调度器(前身直接对比);
5. 单层 LLM 选择器(消融:只选 FJSP 算子);
6. ReflecSched 式自然语言经验方案(输出空间消融);
7. (下界参照)LLM 直接调度,复现三失效。
