# SkySwitch 指挥设计文档
## 面向动态 FJSP–任务分配–MAPF 的因果引导滚动 MCTS 算法组合切换系统

**文档用途**：直接交给编码工具执行。  
**目标**：在现有 SkyEngine 研究原型上，完成一套可运行、可复现、可做论文主实验的“动态算法组合切换”系统。  
**核心原则**：不重写 SkyEngine，不把项目改造成另一个平台；保留现有联合仿真内核，以一个独立的组合搜索层接管 FJSP、Assigner、MAPF 三类算法的在线选择和切换。

---

# 0. 总目标：最终要交付什么

最终系统必须实现以下闭环：

```text
真实/主仿真环境持续运行
        │
        │ 触发事件或性能恶化
        ▼
读取当前联合状态 S_t
        │
        ▼
创建 MCTS 根节点
        │
        ├── 切 FJSP
        ├── 切 Assigner
        ├── 切 MAPF
        └── 联合切换
        │
        ▼
并行克隆当前状态，在隔离 Worker 中执行短期/中期仿真
        │
        ▼
评价每条组合切换路径
        │
        ▼
MCTS 继续扩展有希望的分支
        │
        ▼
达到在线计算预算
        │
        ▼
选择最佳路径的第一个切换动作
        │
        ▼
主环境执行该切换
        │
        ▼
环境继续变化，下一次重新搜索
```

必须同时具备：

1. **FJSP、Assigner、MAPF 三部分均可自由切换**；
2. **MCTS 搜索的是组合切换序列，不是单次算法选择**；
3. **物理仿真时间与算法实际计算时间分别记账，但在线执行时必须耦合推进**；
4. **Docker 用于算法服务隔离、并行 Worker、资源控制和复现**；
5. **因果模块不是口头解释，而是基于同状态克隆和干预实验的反事实归因**；
6. **所有论文结果都能从固定快照、固定种子和实验清单中复现**。

项目临时名：

> **SkySwitch：因果引导的动态算法组合 MCTS**

论文里可以再换名字，不影响实现。

# 1. 现有 SkyEngine 的事实边界

根据现有项目调研，SkyEngine 已经有我们需要的大部分“执行内核”：

- `Coordinator` 每个时间步依次调用：
  1. `JobSolver.plan(...)`
  2. `Assigner.plan(...)`
  3. `RouteSolver.plan(...)`
- 三者最终统一进入 `GridFactoryEnv`；
- 环境已经同时维护：
  - Job / Operation / Machine；
  - RoutingTask；
  - AGV；
  - Pogema 网格；
- 已支持动态事件内核：
  - 机器故障与恢复；
  - AGV 故障；
  - 临时障碍；
  - 加工时间不确定性；
- 运行时插单和特急单已有数据结构、状态机及局部测试，但在线闭环尚未完成：
  - `sim_server.py` 主循环存在残留错误调用；
  - FJSP 服务端没有旧客户端依赖的 `/replan`；
  - `priority/request_id` 尚未贯穿普通 `/plan` 链路；
- 已有三类联合指标：
  - FJSP 指标；
  - MAPF 指标；
  - 耦合指标；
- FJSP 与 MAPF 已经有外部 HTTP / Docker 接入方式；
- Assigner 当前主要是本地注册表，但数量较多，适合作为组合搜索的第三个维度。

**不要重新实现制造仿真环境。**

本项目的重点是：

> 在现有 `Coordinator + GridFactoryEnv` 之上增加“算法组合搜索与切换层”。

# 3. 核心研究问题

动态制造环境中不存在一个始终最好的固定算法组合。

定义一个组合：

\[
c=(f,a,m)
\]

其中：

- \(f\)：FJSP 求解算法；
- \(a\)：AGV 任务分配算法；
- \(m\)：MAPF 路径规划算法。

例如：

```text
(PSO, nearest, EECBS)
(CP-SAT, load_balance, LNS2)
(DE, urgency, LaCAM)
```

动态事件发生后：

\[
S_t \rightarrow S_{t+1}
\]

原组合 \(c_t\) 可能不再适合。

因此目标不是找一个全局固定组合，而是搜索一个序列：

\[
c_t \rightarrow c_{t+1} \rightarrow c_{t+2} \rightarrow \cdots
\]

使制造系统在动态变化下的最终运行结果尽可能好。

# 4. 两套时间必须分别记录，但在线执行必须耦合

这是本项目必须明确写入代码和论文的语义。

## 4.1 物理仿真时间

记为：

\[
t_{\mathrm{sim}}
\]

用于表示：

- 加工持续时间；
- AGV 移动时间；
- 排队；
- 等待来料；
- makespan；
- tardiness；
- 运输延迟。

这是制造系统的时间。

## 4.2 算法计算时间

记为：

\[
t_{\mathrm{cpu}}
\]

实际用 `time.monotonic_ns()` 或等价单调时钟测量。

用于表示：

- MCTS 搜索总耗时；
- 单次 FJSP 调用耗时；
- Assigner 调用耗时；
- MAPF 调用耗时；
- 克隆状态耗时；
- Worker 调度耗时。

## 4.3 主实验口径

主实验：

\[
\min \mathrm{Makespan}_{sim}
\]

约束：

\[
T_{\mathrm{search, wall}} \le B_{\mathrm{search}}
\]

**不要把 1 秒算法 wall-clock 机械地加成 1 秒制造 makespan。**

但是，不能因此暂停主环境。在线决策必须采用：

```text
事件时刻捕获 action-independent snapshot
→ 主环境在搜索 wall-clock 期间继续加工、运输和维修倒计时
→ Worker 在事件快照上并行搜索
→ 搜索结束读取最新物理状态
→ 对候选执行 freshness/rebase
→ 原子激活幸存候选
→ 无安全候选时执行 keep_current
```

因此计算时间不是事后加到 makespan 上，而是通过搜索期间真实发生的状态漂移影响最终
制造结果。冻结快照只允许用于机制诊断、预算校准和反事实解释，不能作为论文在线主实验。

论文必须同时报告：

```text
制造 makespan
搜索 wall-clock
P50 / P95 决策延迟
每次搜索展开节点数
```

可以额外报告冻结时钟诊断实验，用于拆分“算法选择质量”和“实时状态漂移”的影响；
严格实时耦合必须是第一版主实验，而不是后续附加项。

# 5. 为什么使用 MCTS

如果只是当前状态选一个组合：

```text
S_t → best(f,a,m)
```

那只是普通算法选择，不需要 MCTS。

本项目中 MCTS 搜索的是**未来一段时间内的组合切换路径**：

```text
当前组合 c0
     │
     ├── c1
     │    ├── c11
     │    └── c12
     │
     ├── c2
     │    ├── c21
     │    └── c22
     │
     └── c3
```

例如：

```text
PSO + nearest + EECBS
        ↓
CP-SAT + nearest + EECBS
        ↓
CP-SAT + load_balance + LNS2
```

树深度表示：

> 如果先做一次切换并运行一段，再根据新的制造状态继续切换，后续结果如何。

这使“多阶段切换”成为真实的树结构，而不是人为增加深度。

# 6. 从 CEDAR 借什么

参考 CEDAR 的核心思想，但不照搬大模型角色。

CEDAR 的可迁移结构是：

```text
候选系统
→ 修改器提出新候选
→ 实际运行
→ 评价器打分
→ 树搜索选择下一处扩展
```

SkySwitch 对应：

```text
算法组合 + 制造状态
→ 组合调整器提出切换
→ 克隆环境执行
→ 仿真评价器得到数值结果
→ MCTS 选择下一分支
```

映射：

| CEDAR 概念 | SkySwitch |
|---|---|
| 可运行系统候选 | 当前状态 + 算法组合 |
| Editor | 组合调整器 |
| Judge | 仿真评价器 |
| Tree Search | 组合切换 MCTS |
| 分析/解释 | 因果反事实分析 |
| 变体 | 新的 FJSP/Assigner/MAPF 组合 |

重要区别：

> **SkySwitch 的最终价值函数必须来自真实仿真，不由大模型主观打分。**

大模型只允许用于“提出值得尝试的组合”和“把已有因果结果转成自然语言”，不能决定实验数值。

# 7. MCTS 节点定义

```python
@dataclass
class SearchNode:
    node_id: str
    parent_id: str | None
    depth: int

    snapshot_ref: str
    snapshot_hash: str
    sim_time: float

    combo: ComboSpec
    action_from_parent: SwitchAction | None

    rollout_horizon: int
    rollout_result: RolloutResult | None

    metrics: JointMetrics | None
    causal_summary: CausalSummary | None

    visits: int = 0
    value_sum: float = 0.0
    value_sq_sum: float = 0.0
    prior: float = 0.0

    expanded_actions: set[str] = field(default_factory=set)
    terminal: bool = False
```

一个节点表示：

> **在某个克隆制造状态下，采用某个算法组合并运行到一个新的决策点之后得到的状态。**

因此节点不仅有组合，还有新的环境状态。

这是真正的状态树。

# 8. 组合定义

统一三类组件：

```python
@dataclass(frozen=True)
class ComboSpec:
    fjsp: AlgorithmSpec
    assigner: AlgorithmSpec
    mapf: AlgorithmSpec
```

算法统一描述：

```python
@dataclass(frozen=True)
class AlgorithmSpec:
    name: str
    version: str
    mode: Literal["local", "http"]
    endpoint: str | None
    config: dict
    image_digest: str | None
```

必须记录：

```text
算法名
版本
配置
Docker image digest
协议版本
```

不能只记录：

```text
"pso"
```

否则论文无法复现。

# 9. 动作定义

MCTS 的边是算法组合切换。

```python
@dataclass(frozen=True)
class SwitchAction:
    new_fjsp: AlgorithmSpec | None
    new_assigner: AlgorithmSpec | None
    new_mapf: AlgorithmSpec | None
    probe_budget_ms: int
    execution_budget_ms: int | None
```

其中 `None` 表示保持当前组件。

必须存在显式动作：

```text
keep_current
```

其 `probe_budget_ms=0`，始终可用，并作为没有新鲜安全候选时的提交回退。算法动作必须
绑定 `solver + version + config + exact probe budget`，不能只记录算法名。

## 9.1 四类动作

### A. 只换 FJSP

```text
(F1, A1, M1)
→
(F2, A1, M1)
```

### B. 只换 Assigner

```text
(F1, A1, M1)
→
(F1, A2, M1)
```

### C. 只换 MAPF

```text
(F1, A1, M1)
→
(F1, A1, M2)
```

### D. 联合切换

```text
(F1, A1, M1)
→
(F2, A2, M2)
```

第一版限制：

```text
单步最多允许切换 2 个组件
```

三组件同时切换只允许在：

```text
根节点
或
因果模块发现明显三方耦合
```

时进入候选。

这样避免组合爆炸。

# 10. 决策点

不要每一个 GridFactory step 都运行 MCTS。

MCTS 只在决策点触发。

第一版决策点：

```text
机器故障
机器恢复
AGV 故障
AGV 恢复
临时障碍出现
临时障碍消失
批量插单
特急单
固定周期重评估
```

再增加性能触发：

```text
机器等待来料比例连续 K 步超过阈值
AGV 带任务停滞连续 K 步超过阈值
冲突率连续 K 步超过阈值
```

必须有冷却窗口：

```text
min_switch_interval_steps
```

避免组合抖动。

# 11. Rollout 的时间语义

一个树边不能只“调用算法然后立即评分”。

必须运行制造环境一小段。

定义：

```text
H_rollout = 20 / 50 / 100 simulation steps
```

或者：

```text
直到下一个事件
直到一个关键工序集合完成
直到固定仿真时间窗结束
```

第一版推荐：

> 固定 `H_rollout` + episode 快结束时自动截断。

## 11.1 Transition

从节点 \(n\)：

1. 克隆 `snapshot`；
2. 应用算法切换 `a`；
3. 从克隆状态继续仿真 \(H\) 步；
4. 得到新的状态 `S'`；
5. 记录制造指标；
6. 形成 child。

数学上：

\[
(S',R)=\mathrm{Simulate}(S,c',H,\xi)
\]

其中：

- \(S\)：父节点快照；
- \(c'\)：新组合；
- \(H\)：仿真窗口；
- \(\xi\)：外生随机事件流/种子。

---

# 12. 外生随机流必须共享

同一个父节点的不同 child 必须共享相同：

```text
加工时间随机种子
故障随机流
插单随机流
障碍随机流
```

即 common random numbers。

建议：

```python
ExogenousTape(
    processing_seed,
    event_seed,
    insert_seed,
    map_seed,
)
```

父节点 fork child 时复制同一个 tape cursor。

# 13. 节点评价

第一版不要上复杂神经网络。

定义一个“越大越好”的标准化奖励。

## 13.1 主价值

开发阶段先实现简单版：

\[
J=
-w_1 \cdot \hat C_{\mathrm{remain}}
-w_2 \cdot D_{\mathrm{transport}}
-w_3 \cdot W_{\mathrm{material}}
-w_4 \cdot S_{\mathrm{agv}}
-w_5 \cdot C_{\mathrm{switch}}
\]

其中：

- \(\hat C_{\mathrm{remain}}\)：预计剩余完工时间；
- \(D_{\mathrm{transport}}\)：运输额外延迟；
- \(W_{\mathrm{material}}\)：机器等待来料；
- \(S_{\mathrm{agv}}\)：带任务停滞/冲突；
- \(C_{\mathrm{switch}}\)：切换成本。

但是：

**论文主指标仍然是最终 makespan。**

中间奖励只是搜索启发。

## 13.2 最终 rollout

对于 MCTS 当前最有希望的若干叶子，允许：

```text
继续运行到 episode terminal
```

用真实终局 makespan 替换中间估计。

这样：

```text
大多数节点 → 短 rollout
Top-K 节点 → 完整 rollout
```

兼顾速度与准确性。

# 14. MCTS 选择公式

第一版使用简单 PUCT：

\[
\mathrm{Score}(i)
=
Q_i
+
c_{\mathrm{puct}}
P_i
\frac{\sqrt{N_p}}
{1+N_i}
\]

其中：

- \(Q_i\)：节点历史平均价值；
- \(N_i\)：child 访问次数；
- \(N_p\)：父节点访问次数；
- \(P_i\)：组合调整器给出的先验；
- \(c_{\mathrm{puct}}\)：探索强度。

**不要加入过多自创 bonus。**

第一版只允许：

```text
Q + exploration + prior
```

# 15. 渐进扩展

组合空间可能很大：

\[
|F| \times |A| \times |M|
\]

禁止一次把所有组合挂到树上。

使用：

\[
|Children(n)|
\le
\left\lfloor
k(N(n)+1)^\alpha
\right\rfloor
\]

初始建议：

```yaml
progressive_widening:
  k: 1.5
  alpha: 0.5
```

参数只在 development 集调。

# 16. 组合调整器：对应 CEDAR 的 Editor

组合调整器负责：

> 当前节点下一批最值得尝试的切换是什么。

第一版必须有三个版本。

## 16.1 RandomEditor

随机合法切换。

用途：baseline / 测试。

## 16.2 RuleEditor

使用当前指标判断瓶颈。

例如：

```text
机器负载方差高
机器队列长
→ 优先换 FJSP
```

```text
AGV 带任务停滞高
冲突高
→ 优先换 MAPF
```

```text
机器等待来料高
AGV 分配不均
→ 优先换 Assigner
```

```text
运输延迟高 + 机器等待来料高
→ 优先联合 Assigner + MAPF
```

这个版本必须成为第一版默认 Editor。

## 16.3 CausalEditor

利用同状态干预结果估计：

> 改哪个组件最可能改善系统。

详见下一节。

---

# 17. 因果模块：必须单独设计

重要：

> **MCTS 本身不是因果推断。**

论文中不能写：

```text
因为用了 MCTS，所以获得因果解释。
```

正确说法：

> 我们利用可克隆制造模拟器做受控干预，将反事实结果作为 MCTS 的组合先验和最终解释。

---

# 18. 因果问题定义

在相同状态 \(S\)、相同外生随机流 \(\xi\) 下，观察：

\[
Y(f,a,m;S,\xi)
\]

这里 \(Y\) 可以是：

```text
最终 makespan
未来 H 步机器等待来料
运输延迟
AGV 停滞
```

可以执行干预：

\[
do(F=f')
\]

\[
do(A=a')
\]

\[
do(M=m')
\]

甚至：

\[
do(F=f',A=a',M=m')
\]

# 23. 因果模块怎么帮助 MCTS

第一版分两级。

## 23.1 搜索前快速干预

根节点做短 horizon probe：

```text
只换 FJSP 的候选
只换 Assigner 的候选
只换 MAPF 的候选
```

估计：

```text
哪个组件当前最值得改
```

然后生成 prior：

\[
P(a)
=
\mathrm{softmax}
\left(
\frac{\widehat{\Delta}(a)}
{\mathrm{cost}(a)+\epsilon}
\right)
\]

这就是 CausalEditor 的初始先验。

## 23.2 搜索后完整解释

MCTS 选出最终动作以后，再执行完整的：

```text
2^k 局部反事实
```

输出主效应和交互效应。

这个解释不必位于在线关键路径。

# 25. Docker 总体架构

**不要为每一个 MCTS 节点启动一个新容器。**

这样启动开销会污染计算时间，而且效率很差。

正确架构：

```text
                    sky-controller
                    MCTS / 调度器
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
        sim-worker-1  sim-worker-2  sim-worker-N
             │             │             │
             └──────算法服务网络──────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
       fjsp-*          assigner-*         mapf-*
       services         services          services
```

Worker 可以共享网络和无状态服务，但不能共享有进程级 cursor 的 `/plan` 会话。每次
rollout 必须满足以下至少一种：

```text
使用无状态 /solve + request_id
使用显式 session_id 做完整状态隔离
或由单个 Worker 独占有状态 solver
```

禁止不同节点并发复用同一个全局 solver cursor。

# 32. MCTS 主流程

```text
Algorithm: Causal-Guided Rolling Portfolio MCTS

Input:
    当前主环境状态 S_t
    当前组合 c_t
    算法目录 D
    搜索 wall-clock 预算 B
    rollout horizon H

1. export_snapshot(S_t)
2. 创建 root(S_t, c_t)
2.1 主环境启动连续物理推进，不因搜索暂停

3. 运行根节点快速因果 probe
4. 生成候选切换 prior

5. while wall_time < B:
       node = SELECT(root)

       action = EDIT(node)
         - progressive widening
         - causal/rule prior

       child = EXPAND(node, action)
         - clone parent snapshot
         - switch combo
         - same exogenous tape
         - worker rollout H steps

       value = JUDGE(child)
         - manufacturing progress
         - coupled metrics
         - optional terminal rollout

       BACKUP(child, value)

6. 搜索结束
7. 选 root 下访问/价值最优 child
8. 停止搜索并读取主环境最新状态 S_now
9. 对 root child 候选逐个执行 freshness/rebase
10. 删除 stale 或不可原子激活的候选
11. 在幸存候选中输出第一步 switch action；无幸存候选则 keep_current
12. 使用 PlanRevisionActivator / SwitchManager 原子应用
13. 搜索后局部反事实解释不进入在线关键路径
14. 继续运行，等待下一决策点
```

# 33. 最终动作选择

不要直接选“树上价值最大的任意深节点”。

执行的是：

> 最佳路径的第一步。

主版本建议：

\[
a^*=
\arg\max_{a \in child(root)}
N(a)
\]

同时报告：

```text
max Q child
max visit child
```

是否一致。

# 34. 切换语义

FJSP / Assigner / MAPF 切换必须明确。

## FJSP

切换只能影响：

```text
未开始的工序
未被冻结的工序
```

已经加工或进入不可逆阶段的状态不能被新 solver 回滚。

## Assigner

已真正接单并开始运输的 AGV task 默认不重分配。

允许只对：

```text
pending routing tasks
```

使用新 assigner。

## MAPF

已执行的路径前缀不可回滚。

新 MAPF 从当前 AGV 实际位置重新规划未来路径。

# 51. 论文成功判据

真正成功至少需要同时满足：

## 条件 A

\[
\text{Rolling MCTS}
<
\text{Best Fixed}
\]

在 makespan 上有稳定 paired 改善。

## 条件 B

\[
\text{Full MCTS}
<
\text{Depth-1 Search}
\]

证明多阶段树有价值。

## 条件 C

\[
\text{Causal MCTS}
\le
\text{普通 MCTS}
\]

在相同 wall-clock 预算下至少不差，最好明显更好或更省节点。

## 条件 D

至少存在稳定的：

```text
FJSP × Assigner
FJSP × MAPF
Assigner × MAPF
```

交互效应中的一种。

这样才能支撑“联合搜索而不是三个独立 selector”。

# 52. 如果结果不符合预期，怎么科学回退

## Full MCTS ≈ Depth-1

说明系统主要需要状态依赖的一次算法选择，而不是多步搜索。论文不要强行讲 MCTS 深树。

## CausalEditor ≈ RuleEditor

可以保留因果模块用于解释，不宣称提升搜索性能。

## 三组件交互很弱

说明组合接近可分解。论文改成动态三阶段算法组合选择，不要硬讲强耦合。

## 固定组合一直最好

说明当前动态场景不足以产生 portfolio complementarity。

优先检查：

```text
事件强度
场景多样性
算法池是否真正有差异
```

不要继续调 MCTS 参数刷结果。

# 54. 论文最终故事

用最朴素的话：

> 一个动态工厂中，机器调度、AGV 分配和路径规划共同决定制造效率。随着机器故障、AGV 故障、障碍和插单不断发生，固定算法组合会失效。我们把在线控制建模成一个“算法组合连续切换”的树搜索问题：树节点表示当前制造状态及其 FJSP–Assigner–MAPF 组合，树边表示一次算法组件切换。MCTS 在给定实际计算预算内，通过多个隔离的 Docker Worker 并行克隆仿真，搜索未来若干阶段的组合切换路径，并只把最佳路径的第一步应用到主环境。与此同时，我们利用同一状态和同一随机事件流下的受控干预，量化三个组件各自的贡献及交互效应，用于引导搜索并解释为什么需要进行某次切换。

# 56. 总结

实现优先级只有一条：

```text
先让环境可复现
→ 再让状态可克隆
→ 再让三组件可切换
→ 再做并行 rollout
→ 再做 Depth=1
→ 再做 MCTS
→ 再做滚动切换
→ 再做因果干预
→ 最后才做大模型增强
```

不能倒过来。

如果编码工具开始：

```text
先写复杂 MCTS
先训练神经网络
先做 LLM Agent
先改大架构
```

直接停止并拉回当前 Phase。

**本项目的核心不是模块越多越好，而是证明：动态制造状态变化会改变 FJSP–Assigner–MAPF 的最优组合，而受计算预算约束的滚动 MCTS 能利用这种状态依赖，通过多阶段组合切换获得稳定收益，并能够用受控反事实实验解释收益来自哪里。**
