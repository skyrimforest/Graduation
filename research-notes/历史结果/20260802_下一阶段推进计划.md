# SkyEngine 下一阶段推进计划

**版本：2026-08-02**

## 1. 当前优先级

下一阶段不训练新网络，按以下顺序推进：

1. 冻结数据契约和 CPU/GPU Docker profile；
2. 修复 episode 终止性并审计指标；
3. 建立静态时间、局部路由和 MAPF oracle 三层基线；
4. 完成“路径反馈是否值得研究”的反证实验；
5. 再决定是否开发风险模型与预算化重调度。

## 2. Gate 0：冻结可复现运行入口

### 任务

- 将 `J10P5M6.json` 等测试实例放入统一的 `dataset/fjsp/` 契约；
- 将地图统一为 `dataset/mapf/<file>.yaml`，文件内容直接以地图名为 key；
- `run.py` 启动时检查目录、文件和实例名，错误应在环境创建前报告；
- Docker Compose 增加 `cpu` 默认模式，GPU 求解器使用可选 profile；
- 固定一个不依赖外部 HTTP/GPU 的 lifecycle 命令；
- 测试输出不要每步重复打印 PASS，只保留前 3 步、周期心跳和最终汇总。

### 验收

```text
docker compose --profile cpu run --rm engine \
  uv run python test/env_test/test_lifecycle.py
```

应在无需临时复制数据的情况下执行。

## 3. Gate 1：终止性和指标审计

### 已知失败

2026-08-02 实测：

- `530/532 PASS`；
- 500 步完成 `8/10` Job；
- 完成 `46/50` Operation；
- episode 没有 `job_done`。

### 需要定位

- 剩余 4 道 Operation 的状态和所属 Job；
- 对应运输任务处于 pending、assigned、active 还是 finished；
- AGV 是否持续移动但不能到达；
- 目标机器是否占用或 Operation 前序状态错误；
- A* 随机动作是否造成长路径和抖动；
- Pogema `on_target`、collision system 和目标更新是否影响收敛；
- 500 步是否只是 horizon 过短，而非逻辑死锁。

### 必加字段

每个 episode 汇总：

```text
completed
termination_reason
valid_metrics
used_mock
fallback_solver
unfinished_jobs
unfinished_operations
pending_transfers
active_transfers
mapf_calls
reschedule_calls
```

### 验收

- 小型实例 20/20 seeds 完成；
- 中型实例完成率至少 95%，否则未完成必须有明确原因；
- 完成 episode 的 makespan > 0；
- 事件日志可重新计算 makespan、机器等待和 AGV 时间；
- 未完成 episode 不得混入正常 makespan 均值。

## 4. Gate 2：建立路径执行层级

### Level 0：静态运输

- Manhattan/BFS 最短路；
- 不执行车辆冲突；
- 作为理论乐观下界。

### Level 1：局部反应式执行

- 当前 A* + Pogema；
- 将 `random_rate` 固定为 0；
- 明确记录 vertex/edge conflict、stationary 和 detour；
- 作为低成本在线基线。

### Level 2：MAPF oracle

优先复用已有仓库：

1. LaCAM 或 PIBT：中大规模可扩展基线；
2. PBS/ECBS：小中规模高质量 oracle；
3. SIPP/RHCR：后续滚动时域扩展。

统一接口建议：

```python
MapfQuery(
    map_id,
    starts,
    goals,
    release_times,
    service_times,
    existing_reservations,
    time_limit,
)

MapfResult(
    status,
    paths,
    arrival_times,
    conflicts_resolved,
    sum_of_costs,
    makespan,
    runtime_ms,
)
```

### 验收

- 同一输入可切换 local A*、PIBT/LaCAM 和 oracle；
- 所有结果包含运行时间和可行状态；
- 路径无顶点与对向边冲突；
- oracle 超时被标记，不静默回退。

## 5. Gate 3：反证实验

目标是回答：**真实路径反馈是否足以改变 FJSP 决策和 makespan？**

### 实验矩阵

- 地图：开阔、单瓶颈、双瓶颈；
- AGV 数：2、4、8；
- 任务释放：平滑、波次；
- 跨区运输比例：低、中、高；
- FJSP 实例：小型和中型各至少 3 个；
- seeds：每格至少 5 个。

### 方法

1. 静态 BFS；
2. 历史均值估计；
3. 局部 A* 执行；
4. 每次调用 MAPF oracle；
5. 固定周期调用 oracle。

### 指标

- 预测运输时间 vs 实际运输时间；
- 真实 makespan；
- 机器等待入站物料时间；
- AGV 等待、空驶和绕行；
- oracle 次数和总运行时间；
- 完成率与超时率。

### 决策标准

若中高拥堵下“静态/均值”相对 oracle 的真实 makespan gap 小于预先设定阈值，例如 3%，则不进入复杂风险模型；改做基准与失效边界论文。

## 6. Gate 4：运输时延风险模型

仅在 Gate 3 证明问题成立后开发。

### 第一版特征

- BFS 距离；
- AGV 到 pickup 的距离；
- 当前 AGV 工作量；
- 起终点局部占用；
- 路径瓶颈数、最小通道宽度；
- 共享最短路边比例；
- 同波次任务数；
- 目标机器空闲/队列状态；
- 最近窗口平均延迟和 P90。

### 第一版模型

- 历史均值；
- 线性/岭回归；
- LightGBM quantile 或 Gradient Boosting quantile；
- 小型 MLP quantile。

暂不使用复杂 GNN。只有传统模型在跨地图泛化明显不足时，再增加图编码。

### 输出与损失

预测：

```text
P50 travel time
P90 travel time
probability of timeout/infeasibility
```

评价：

- MAE/RMSE；
- pinball loss；
- P90 empirical coverage；
- calibration error；
- 未见地图/AGV 数下的性能。

## 7. Gate 5：预算感知触发与滚动重调度

### 触发器基线

1. Never：从不调用 oracle；
2. Always：每个决策点调用；
3. Periodic：固定周期；
4. Error-triggered：实际误差超阈值；
5. Risk-triggered：预测 P90 超过 slack；
6. Budget-aware：结合剩余预算和关键路径价值。

### 简单预算策略

为每个候选查询估计价值：

\[
\operatorname{VOI}_t =
P(\text{delay affects critical path}\mid s_t)
\cdot \mathbb{E}[\text{avoidable delay}\mid s_t]
- \eta c_{\text{MAPF}}
\]

当 `VOI > threshold` 且剩余预算大于 0 时调用 oracle。

### 滚动重调度范围

依次比较：

1. 只重新分配 AGV；
2. 重新排序未开始 Operation；
3. 重新选择尚未开始 Operation 的机器；
4. 完整滚动时域联合重排。

这样可以证明收益是否真的来自“MAPF 反馈改变 FJSP”，而不是只改车辆分配。

## 8. 最小论文实验包

### 表格

1. 生命周期和执行正确性；
2. 静态/均值/local/oracle 的失效差异；
3. 风险预测准确性和校准；
4. Never/Always/Periodic/Risk/Budget 的主结果；
5. 仅 AGV 重分配 vs 重开机器/工序决策；
6. 地图、实例和 AGV 数外推。

### 图

1. 系统事件与反馈链；
2. 运输时间误差随拥堵变化；
3. makespan-计算成本 Pareto 曲线；
4. 典型瓶颈地图上的任务与路径时间线；
5. oracle 触发时刻和关键路径变化。

### 统计规范

- 每个主要结果至少 5 seeds，最终主结果建议 10 seeds；
- 报告均值、标准差、95% CI 和配对检验；
- 所有策略使用相同 wall-clock 或 oracle 次数预算；
- 训练、验证、测试按实例和地图划分；
- 超时和未完成 episode 计入失败率。

## 10. 两周近期安排

### 第 1 周

- 修复 dataset 和 Docker profile；
- 将生命周期测试输出降噪；
- 定位 8/10 Job 未完成原因；
