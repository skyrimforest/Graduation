# SkyEngine 项目进展审计与选题优化

**审计日期：2026-08-02**

## 1. 结论

项目已经具备可继续推进的工程基础，但尚未具备可直接支撑论文结论的实验基础。

当前最合理的策略不是换掉 FJSP + MAPF 场景，也不是继续扩张“多专家蒸馏 + GRPO + 多塔网络”，而是将选题收敛为：

> **受限 MAPF 查询预算下的风险感知闭环滚动柔性车间调度**

英文建议：

> **Budget-Aware Risk-Triggered Rolling-Horizon Scheduling for Flexible Job Shops with Explicit Multi-Agent Path Execution**

该题研究：在精确 MAPF 查询和全量重调度都较昂贵时，如何预测运输执行风险，并选择何时调用 MAPF oracle、何时重新打开机器/工序决策，以最小化真实端到端 makespan。

## 3. 本次代码审计结论

### 3.1 已实现的闭环

代码中可以确认以下真实数据流：

1. JobSolver 为 Operation 选择机器并生成 `RoutingTask`；
2. Assigner 将待运输任务分配给空闲 AGV；
3. RouteSolver 每个时间步为 AGV 生成移动动作；
4. AGV 到达后写入 `Operation.arrive_machine_at`；
5. 目标 Machine 开始加工并更新 Operation 状态；
6. 完工后释放 Job 的下一道工序。

因此，可以声称“已有事件级联合执行原型”，但暂时不能声称“已有完整联合优化算法”。

### 3.2 当前 RouteSolver 不等价于全局 MAPF

内置 `AStarRouteSolver` 为每辆车在局部观测中独立规划下一步：

- 每个 agent 各自维护 A*；
- 将其他车辆当前位置视为障碍；
- 没有联合时空 reservation table；
- 没有 CBS/PBS 的冲突树或优先级搜索；
- 没有显式保证全局完备性或最优性；
- 默认还有 `random_rate=0.2` 的随机动作。

Pogema 会处理同时移动的冲突，但这更接近局部反应式避碰，不应在论文中表述为“使用精确 MAPF 求解器完成全局无冲突路径规划”。

建议区分三个执行层级：

| 层级 | 当前状态 | 论文表述 |
|---|---|---|
| Reactive local routing | 已有 A* + Pogema | 局部冲突感知网格执行 |
| Scalable MAPF | 仓库已有 PIBT/LaCAM，未完成主链路验收 | 待接入基线 |
| MAPF oracle | CBS/PBS/ECBS/SIPP-RHCR 尚缺 | 新选题需要补齐 |

### 3.3 当前运输时间估计器只做到均值反馈

`TransferTimeEstimator` 已实现：

- 机器间 BFS 最短路；
- 已完成运输任务的历史均值校正；
- 滑动窗口；
- 预留但未实质使用的拥堵权重。

尚未实现：

- 条件分位数 P50/P90；
- CVaR 或置信区间；
- 地图瓶颈、路段占用和任务波次特征；
- 风险校准；
- MAPF 查询预算；
- 风险触发重调度。

这使优化后的题目可以在现有代码上增量开发，不需要推翻系统。

### 3.4 Coordinator 仍是同一步串行拼接

`Coordinator.decide()` 当前顺序为：

1. JobSolver 计划；
2. Assigner 分配；
3. RouteSolver 规划。

JobSolver 可以接收 `transfer_time_estimator`，但尚未看到以下机制：

- 路径不可行证书反馈；
- 运输 P90/CVaR 写入调度代价；
- 决定是否重新打开机器选择；
- 固定/自适应滚动时域；
- MAPF 调用预算管理。

因此，现阶段是“有反馈特征的执行链”，不是主从分解、Logic-based Benders 或滚动联合优化。

## 4. Docker 运行审计

### 4.1 构建结果

在宿主机不安装 Python 依赖，使用 Docker 完成：

```text
docker compose build engine
```

镜像 `skyengine:latest` 构建成功。

### 4.2 Compose 直接运行问题

`docker compose run` 在当前 macOS 环境失败，原因是 compose 强制申请 NVIDIA GPU：

```text
could not select device driver "nvidia" with capabilities: [[gpu]]
```

CPU 生命周期测试本身不需要 GPU。建议将 GPU deploy 配置放到可选 profile，默认 engine 使用 CPU。

### 4.3 数据契约问题

测试默认寻找：

- `/dataset/fjsp/J10P5M6.json`
- `/dataset/mapf/10-medium-mazes-part1.yaml`

稳定目录实际是：

- `dataset/fjsp-instances/`，主要为 txt 格式；
- `dataset/mapf/medium_maps.yaml`；
- `J10P5M6.json` 位于另一个仓库 `SkyEngine-FJSP/data/fjsp-master/`。

本次通过临时 Docker 挂载和复制补齐数据契约后运行测试，没有修改原项目文件。

### 4.4 生命周期测试结果

执行：

```text
DATA_DIR=/tmp/skydata uv run python -u test/env_test/test_lifecycle.py
```

结果：

```text
Phase 1 Summary: 530/532 PASS, 2 FAIL
```

两个失败项：

```text
Episode 正常终止 (job_done=True): FAIL
所有 Job 完成 (8/10): FAIL
```

关键观测：

- 500 步内完成 `8/10` 个 Job；
- 加工完成 `46/50` 道 Operation；
- 运输和 Operation 时间戳检查通过；
- 加工步数与 `proc_time` 一致；
- AGV 统计与环境时间一致；
- 没有触发测试定义中的长时间卡死；
- 机器利用率仅约 `3.2%` 到 `6.0%`；
- 4 辆 AGV 的载货时间很长，但机器利用率很低，说明运输/路由成为主要瓶颈。

这证明闭环执行链真实存在，也证明拥堵/运输问题有研究价值；但 episode 未完成意味着现有结果 CSV 不能直接作为论文证据。

## 5. 现有论文叙事的风险

### 5.1 “首个统一环境”不成立

2023 年已有 conflict-free FJSP，2025 年 ACES 联合机器映射与 MAPF，2026 年已有 DQN+PBS 和 CP-FJSPT-H。可以强调可复现环境、预算化闭环和执行风险，但不能继续强调“首个 FJSP-MAPF 联合框架”。

### 5.2 “完整 MAPF 闭环”证据不足

当前主链路的 A* 是局部反应式路径规划。论文必须先接入至少一个可识别的 MAPF 基线，如 PIBT/LaCAM/PBS/ECBS，再讨论 MAPF 反馈。

### 5.3 多专家/GRPO 与核心问题脱节

多专家和 GRPO 只有在以下条件同时满足时才可能成为贡献：

1. 专家输出位于共同的任务-AGV动作空间；
2. 专家在不同拥堵状态下有稳定互补性；
3. 完整方法显著优于最佳单专家、固定权重、BC/PPO；
4. 收益在实例外和地图外仍存在。

当前更紧急的问题是环境终止性、数据契约、MAPF oracle 和闭环对照。多专家相关代码应保留，但暂停作为主线投入。

## 6. 优化后的研究问题

### 6.1 一句话定义

FJSP 调度器通常使用固定或历史平均运输时间，但真实多车路径执行具有拥堵风险。能否在有限 MAPF 查询预算下预测运输时延风险，只在必要时调用精确路径求解和滚动重调度，从而获得更好的 makespan-计算成本 Pareto 前沿？

### 6.2 形式化目标

在每个决策时刻 \(t\)，系统可选择是否调用 MAPF oracle：

\[
q_t \in \{0,1\}, \qquad \sum_t q_t \le B
\]

其中 \(B\) 是 episode 的 MAPF 查询预算。优化目标可以写为：

\[
\min_\pi \; \mathbb{E}[C_{\max}]
+ \lambda \operatorname{CVaR}_{\alpha}(C_{\max})
+ \beta \sum_t q_t c_{\text{MAPF}}
+ \gamma \sum_t r_t c_{\text{reschedule}}
\]

其中 \(r_t\) 表示是否触发滚动重调度。

### 6.3 建议的三项贡献

1. **执行感知基准与闭环协议**  
   将 FJSP 实例、车间地图、AGV 数和任务波次组合成可复现 benchmark；明确静态时间、局部路由和 MAPF oracle 三种执行层级。

2. **校准的运输时延风险模型**  
   对候选机器/任务/AGV 预测 P50、P90 或 CVaR；模型先使用 LightGBM/MLP 分位数回归，验证必要后再升级 GNN。

3. **预算感知的风险触发滚动重调度**  
   根据预测风险、实际偏差和关键机器饥饿风险决定是否调用 MAPF oracle，并在固定预算下重新优化机器和工序选择。

### 6.4 与最近邻工作的差异

| 最近邻工作 | 已覆盖 | 本选题需要证明的新增价值 |
|---|---|---|
| Sensors 2026 DQN + PBS | JSP 排产 + PBS 路径 | FJSP、执行风险、预算化 oracle、风险触发重调度 |
| CP FJSPT-H 2026 | 异构车辆、分区、固定路径预留 | 动态 MAPF 执行、有限查询预算、在线风险 |
| ACES 2025 | 机器映射 + 路径、稳态吞吐 | 有限订单 makespan、执行偏差和滚动决策 |
| IEEE TSMC 2025 | 动态 FJSP + AGV 分配 MARL | 显式路径冲突、校准风险和计算成本 |
| TAPF-PTC 2024 | 前序/时间约束 + CBS | 机器柔性与生产队列的反向重优化 |

## 7. 论文可证伪假设

| 假设 | 对照 | 通过标准 |
|---|---|---|
| H1：静态时间在拥堵下系统性低估运输时间 | BFS/历史均值 vs MAPF 执行 | 延迟误差、机器饥饿、makespan 随拥堵显著增大 |
| H2：风险预测优于均值预测 | Mean vs P90/CVaR | P90 覆盖率校准，并降低高分位 makespan |
| H3：选择性查询优于两个极端 | Never vs Always vs Triggered | 相同预算或相同求解时间下 Pareto 更优 |
| H4：重开机器选择有额外价值 | 只改 AGV vs 机器/工序滚动重排 | 在高拥堵下真实 makespan 稳定下降 |
| H5：结论可以外推 | 未见地图/实例/车数 | 优势不依赖单一训练配置 |

## 8. 继续与停止条件

### 继续主线

满足以下条件后进入风险模型阶段：

- 一个固定 seed episode 可正常完成；
- PIBT/LaCAM 或 PBS/ECBS 至少一个接入主链路；
- 静态时间与真实路径执行在中高拥堵下存在可重复差异；
- 事件日志可以复算 makespan、等待与 oracle 调用成本。

### 停止或降级

满足任一条件时不做风险学习：

- 修复终止性后，静态时间与 MAPF 执行差异很小；
- MAPF 查询成本在实验规模下可以忽略，`always query` 已全面最优；
- 简单历史均值已经达到与分位数模型近似的结果；
- 主链路无法稳定运行足够多的 seed。

此时可降级为：

> **FJSP 调度与多种 MAPF 执行器的可复现耦合基准及失效边界研究。**
