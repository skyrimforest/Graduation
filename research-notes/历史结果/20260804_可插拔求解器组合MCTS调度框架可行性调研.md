# 可插拔求解器组合 MCTS 调度框架可行性调研

日期：2026-08-04

## 一、结论

推荐将论文方法重新抽象为：

> 面向动态制造事件的、计算预算约束下的 FJSP-MAPF 求解器组合元调度框架。

MCTS 是第一种搜索型 `DecisionBackend`，不是系统本身。其前置对照是 fixed、
priority 和 portfolio 策略后端。后续可以在保持状态、动作、约束、奖励和求解器
接口不变的前提下，替换为：

- 规则或线性选择器；
- GNN 调度网络；
- PPO/Actor-Critic；
- Offline RL/IQL；
- policy/value network 引导的 PUCT；
- 其它组合优化或超启发式方法。

该方向工程可行，科研潜力中高，但必须满足两个前提：

1. FJSP/MAPF solver portfolio 相对最佳固定组合存在显著 oracle headroom；
2. 元调度器能在相同在线计算预算下稳定缩小到 oracle portfolio 的 regret。

如果没有 portfolio headroom，MCTS 或 RL 都没有可学习、可搜索的选择价值。

本次接口、BNN 与因果路线的冻结协议见：
[`20260804_DecisionBackend与学习后端演进协议.md`](20260804_DecisionBackend与学习后端演进协议.md)。

## 二、术语纠正

有限时间内，MCTS 通常只能返回：

```text
best-so-far / near-optimal / low-regret solution
```

不能宣称有限时间内获取“最优解”，除非底层 exact solver 已提供最优性证明。

论文应使用：

```text
budgeted anytime decision-making
best solution under a wall-clock budget
regret to oracle portfolio
```

## 三、前沿证据

### 3.1 MCTS 用于 FJSP/DJSS 已不是空白

已有直接工作包括：

- Li 等人在 *Computers & Industrial Engineering* 2021 研究 dynamic FJSP 的
  MCTS makespan 优化；
- Saqlain 等人在 *Flexible Services and Manufacturing Journal* 2023 提出
  MCTS-FJS；
- 2025 年已有带 transportation-time constraints 的 enhanced MCTS；
- 2022 WSC 已出现 dynamic job shop + AGV 的 MCTS。

参考：

- [MCTS-FJS, 2023](https://doi.org/10.1007/s10696-021-09437-4)
- [DyRo-MCTS discussion and related-work list](https://openreview.net/forum?id=wr3J8niaos)
- [本地 DyRo-MCTS 原文](papers/2025_DyRo-MCTS_Dynamic_Job_Shop_Scheduling.pdf)

因此，“将 MCTS 用于动态 FJSP”本身不具备足够新颖性。

DyRo-MCTS 在 ICLR 2026 投稿中报告了动态到达场景收益，但最终被拒。Meta
review 的主要问题是：

- 只修改 UCT exploitation/robustness 项，创新有限；
- 与既有 dynamic JSSP MCTS 比较不充分；
- 计算开销和广泛适用性论证不足。

这对本项目是直接警示：不能只设计一个新的 UCT 打分项。

### 3.2 动态 FJSP-AGV 的学习调度已有强基线

IEEE TSMC 2025 已提出面向 dynamic FJSP with AGVs 的多智能体强化学习框架，
联合处理 task selection、machine allocation 和 AGV allocation，并在四类
disturbance events 上实验。

参考：

- [Real-Time Scheduling for Flexible Job Shop With AGVs, TSMC 2025](https://doi.org/10.1109/TSMC.2024.3520381)
- [本地书目与获取状态](papers/metadata/2025_Li_DFJSP_AGV_MARL.md)

我们的区别不能只是“把 MARL 换成 MCTS”，而应是：

- 显式 collision-free MAPF；
- 真实 empty/loaded transport；
- 可切换的 FJSP/MAPF solver portfolio；
- 统一事件动作契约；
- 端到端 makespan；
- 同源物理反事实和严格在线计算预算。

### 3.3 MAPF 确实适合算法组合选择

MAPF 领域没有单一算法在所有实例、时间预算和质量目标上占优。已有工作明确研究
CBS、EECBS、PP、PPS、PIBT 等 solver/hyperparameter selection，并强调 runtime
和 solution cost 的目标不同，不能共用一套 loss 或评价方法。

参考：

- [No Panacea in Planning: Algorithm Selection for Suboptimal MAPF](https://arxiv.org/abs/2404.03554)
- [Algorithm Selection for Optimal MAPF via Graph Embedding](https://arxiv.org/abs/2406.10827)
- [Automatic Algorithm Selection in MAPF](https://arxiv.org/abs/1906.03992)

这为 MAPF portfolio 提供了直接理论和实验依据。

### 3.4 单步路径质量不等于端到端制造收益

Anytime PIBT 证明单步 MAPF 解可在给定预算内持续改进，但其论文也观察到：

> 改善 single-step solution quality 不一定显著改善 full-horizon cost。

参考：

- [Anytime Single-Step MAPF Planning with Anytime PIBT](https://arxiv.org/abs/2504.07841)

因此不能用 MAPF flowtime 或单次冲突数代替制造 makespan，仍必须保留当前
terminal Value Gate。

### 3.5 模块化调度环境与可替换策略是合理趋势

JobShopLib 强调将 graph representation、features、action space、reward 和策略
拆成可组合模块；POGEMA 则提供经典规划、学习方法和统一评测环境。

参考：

- [JobShopLib modular RL environment](https://arxiv.org/abs/2506.13781)
- [POGEMA benchmark platform](https://arxiv.org/abs/2407.14931)

FJSP 最新方法也在从纯 constructive policy 转向 improvement search。NeurIPS
2025 MIStar 使用异构图、memory-enhanced GNN 和 improvement search，并在评审中
被追问 machine breakdown、动态到达、扩展性和训练成本。

参考：

- [MIStar, NeurIPS 2025](https://openreview.net/forum?id=sdlLycSeZl)

这些工作支持“统一环境 + 可替换决策后端”，但也说明仅有软件模块化不构成论文
算法贡献。

## 四、推荐系统抽象

### 4.1 总体架构

```text
SkyEngine physical state
        |
        v
EventAdapter
  machine / AGV / road / urgent order
        |
        v
ActionGenerator + FeasibilityMask
        |
        v
DecisionBackend
  rule / MCTS / GNN / PPO / IQL / hybrid PUCT
        |
        v
SolverPortfolio
  FJSP proposals + MAPF proposals
        |
        v
BudgetManager + PhysicalTransition
        |
        v
PlanRevision / route artifact activation
```

### 4.2 核心接口

```python
class DecisionBackend:
    def decide(
        self,
        decision_state,
        legal_actions,
        solver_portfolio,
        budget,
    ) -> Decision:
        ...
```

`DecisionBackend` 只依赖统一契约，不直接依赖某个事件或 solver。

```python
class DecisionState:
    physical_snapshot
    event_context
    residual_fjsp
    active_transports
    reservation_state
    solver_artifacts
    elapsed_budget
```

```python
class Decision:
    recovery_operator
    operator_parameters
    fjsp_profile
    mapf_profile
    compute_budget
```

### 4.3 SMDP 而非普通 MDP

制造动作持续时间不同：

- 等待 8 个 step；
- 一次改派可能持续到取料；
- 局部重调度有不同 solver latency；
- MAPF 路径持续多个 step。

因此统一决策接口应按 Semi-Markov Decision Process 建模：

```text
(state, action, duration, cumulative_cost, next_state)
```

否则 RL 和 MCTS 会对长短动作产生错误的 reward 比较。

## 六、Solver Portfolio

### 6.1 FJSP profiles

首轮不建议枚举所有镜像，应选择行为差异明显的 3–4 个 profile：

```text
fast_dispatch
greedy_transport_aware
cp_sat_local_1s
cp_sat_local_5s
```

后续再接入其它 FJSP Docker solver。所有 profile 通过统一 `/solve` artifact
contract 输出，不要求修改各 solver 镜像。

### 6.2 MAPF profiles

建议首轮：

```text
liveness_local_astar
pibt
lacam
eecbs
mapf_lns2
```

但不是所有算法都适合在线 lifelong manufacturing：

- EECBS 质量有界但可能超时；
- PIBT 快但偏贪心；
- LaCAM/PIBT 适合快速找到可行路径；
- MAPF-LNS2 适合在有额外预算时继续改进；
- remote solver 的 warm start 和 fork restore 必须单独验证。

### 6.3 不做完整笛卡尔积

完整：

```text
event action × FJSP solver × MAPF solver × hyperparameters
```

会造成不可控 branching factor。

应构造少量 `SolverProfile`：

```text
fast:
  greedy_transport_aware + PIBT

balanced:
  cp_sat_local_1s + LaCAM

quality:
  cp_sat_local_5s + EECBS

anytime:
  greedy_transport_aware + MAPF-LNS2
```

profile 必须记录：

- wall-clock budget；
- feasible/timeout/failure；
- artifact hash；
- objective/bound；
- warm-start 能力；
- state restore 能力。

## 七、MCTS 后端

### 7.1 推荐 Open-Loop Progressive-Widening MCTS

SkyEngine 状态巨大且含随机事件，不适合按完整物理状态做 transposition table。
推荐树节点表示动作序列，而不是哈希后的完整状态：

```text
node = recovery action sequence
```

每次 simulation 从 root snapshot 重新 fork，并使用独立 planning seed 回放。

### 7.2 分层树

```text
Event operator node
    -> operator parameter node
        -> solver profile node
            -> physical transition / chance
```

Progressive Widening：

```text
|children(s)| <= k * N(s)^alpha
```

访问次数较小时只展开快速 profile，预算增加后逐步加入高质量 solver。

### 7.3 多保真度

```text
deep rollout:
  fast FJSP + PIBT/local A*

promising root children:
  CP-SAT + LaCAM/EECBS/LNS2 refinement
```

昂贵 solver 不应在每个叶节点调用。

### 7.4 防止未来泄漏

```text
planning RNG != execution RNG
```

候选 action 在同一次 simulation 中共享 common random numbers；实际执行使用独立
随机流。MCTS 不得使用测试 episode 的 realized future events。

### 7.5 在线执行

MCTS 只执行 root action，经过固定 decision interval 或物理 milestone 后重新
规划：

```text
search -> execute first action -> observe -> reuse subtree -> search
```

## 八、如何替换为 RL 或神经网络

### 8.1 规则后端

```text
state -> hand-crafted priority -> action
```

用于 baseline 和安全回退。

### 8.2 监督式调度网络

MCTS 可生成：

```text
state
root visit distribution
root Q estimates
selected solver profile
```

用于训练：

```text
policy network: state -> action/profile prior
value network: state -> expected remaining makespan
```

### 8.3 PUCT / AlphaZero-style

训练后的 policy/value network 不直接替代物理约束，而是：

- policy 提供 MCTS prior；
- value 减少长 rollout；
- feasibility mask 保证动作合法；
- SkyEngine 仍执行真实 transition。

### 8.4 Online RL

PPO/Actor-Critic 可以实现相同 `DecisionBackend`，但要求：

- 固定 SMDP state/action/reward；
- action masking；
- variable-duration return；
- OOD event/state 检测；
- 安全 fallback。

### 8.5 Offline RL

MCTS 日志可以形成离线数据：

```text
(state, legal_actions, action, duration, cost, next_state)
```

但只有在 behavior coverage、terminal correctness 和跨实例泛化 Gate 通过后，才
允许启用 IQL/CBQ-IQL。当前仍应阻塞。

## 九、与现有工作的差异化

不足以构成贡献：

- vanilla MCTS；
- 给 UCT 增加一个手工权重；
- 单独做 FJSP solver selection；
- 单独做 MAPF solver selection；
- 只实现可替换 Python 接口。

可能形成强贡献的组合：

1. 统一四类制造事件的 typed action/SMDP contract；
2. 对 FJSP schedule proposal 与 collision-free MAPF proposal 做联合 portfolio；
3. 在严格 wall-clock budget 下使用 progressive widening 和 multi-fidelity；
4. 以真实 empty/loaded transport 和 terminal makespan 评价；
5. 对 MCTS、规则、网络和 RL 使用同一 backend contract；
6. 同源反事实、独立规划随机流和跨实例/拓扑/event holdout。

论文方法名称应突出：

```text
Budgeted Event-Driven Solver-Portfolio Planning
```

而不是只突出 MCTS。MCTS 是主要实例化方法。

## 十、工程可行性

### 已具备

- 完整 snapshot/fork；
- Python/NumPy/processing/event RNG state；
- coordinator/job/MAPF state restore；
- PlanRevision 激活与回滚；
- stateless FJSP `/solve` artifact；
- MAPF solver factory；
- event-specific action registry；
- terminal physical invariants；
- solver artifact cache；
- branch isolation。

### 主要缺口

1. `DecisionBackend` typed contract 和首批策略后端已实现，但 SMDP transition
   contract 尚未接入；
2. 多 FJSP service 的 profile registry、真实 profile activator 和预算控制；
3. MAPF backend 切换时 reservation/warm-start 的一致性；
4. open-loop MCTS tree、progressive widening 和 subtree reuse；
5. wall-clock cancellation/timeout；
6. solver failure 的结构化 fallback；
7. portfolio oracle/headroom 数据。

| 项目 | 评级 |

| 调度器接口抽象 | 高可行 |
| MCTS 接入 snapshot/fork | 中高可行 |
| 多 FJSP solver portfolio | 中高可行 |

| 四事件统一动作空间 | 中高风险 |
| RL 后端替换 | 中等可行，依赖数据 |

## 十一、实验推进顺序

### 第一阶段：Portfolio Headroom Gate

先不实现完整 MCTS。

分别筛查：

```text
FJSP diversity:
  多 FJSP profiles + 固定 robust MAPF

MAPF diversity:
  固定 schedule + 多 MAPF profiles
```

只有单侧均存在差异后，再组成 4–6 个联合 profiles。

指标：

- completion；
- terminal makespan；
- planning wall time；
- timeout/failure；
- best fixed profile；
- per-case oracle profile；
- oracle regret；
- winner diversity。

通过条件应预注册：

```text
oracle portfolio vs best fixed mean improvement > 0
cluster-bootstrap 95% CI lower > 0
至少 20% independent clusters 的 winner 不同
winner 覆盖至少 2 FJSP 和 2 MAPF profiles
```

不通过则停止 portfolio MCTS。

### 第二阶段：MCTS Search Gate

严格 deadline、simulation admission、未完成 rollout 处理和 root coverage 规则见：

```text
20260805_严格Deadline与AnytimeMCTS设计方案.md
```

固定相同 wall-clock budget，比较：

```text
best fixed profile
static profile selector
flat short rollout
vanilla UCT
progressive-widening portfolio MCTS
oracle portfolio
```

核心指标：

```text
regret closed =
(M_fixed - M_mcts) / (M_fixed - M_oracle)
```

同时报告 p50/p95 decision latency。

### 第三阶段：跨事件泛化

训练/开发：

```text
机器故障 + 部分 AGV 故障
```

验证：

```text
未见 FJSP instances
未见 map topologies
道路阻塞
紧急订单
```

如果算法只能在机器故障上有效，就不能宣称统一事件调度器。

### 第四阶段：可替换后端

论文首版不建议同时训练大量 RL：

1. rule backend；
2. portfolio MCTS backend；
3. 一个轻量 policy/value network 作为 MCTS prior 或蒸馏模型。

这已经足以证明接口可替换。PPO/IQL/CBQ-IQL 可作为后续工作，除非前述 Gate 全部
通过且数据量足够。

## 十二、最终判断

该思路比继续修单一机器故障解析估计器更有潜力，原因是：

- 它能真正消费现有多个 FJSP/MAPF 算法；
- 它可以在 Deadline Infrastructure Gate 完成后适配严格在线计算预算；
- 它能统一四类动态事件；
- 它为 MCTS、RL 和简单网络提供同一决策接口；
- 它把论文贡献从单一启发式提升为联合 solver-portfolio planning。

但应保持严格边界：

> 先证明 portfolio 有 headroom，再实现 MCTS；先证明 MCTS 在等预算下缩小
> oracle regret，再训练 RL。

开发 Portfolio Headroom Gate 已通过。当前推荐下一步是严格
Deadline/Cancel/Fallback Infrastructure Gate；通过后再进入 bounded MCTS Search
Gate，而不是直接开发 RL 或神经模型。

策略后端和真实 `profile_activator` 已经落地。FJSP 激活会替换 online gateway 并
清除 artifact cache；MAPF 激活会切换真实 endpoint/config 并清除 remote trajectory
状态，在 loaded transport 存在时会在任何 mutation 前拒绝切换。

2026-08-05 单侧预实验结果：

- MAPF：20 个独立 cluster、三个 200 ms profile；oracle 相对 best fixed 平均降低
  14.95 steps，cluster-bootstrap 95% CI 为 `[8.65, 22.40]`，75% cluster 的
  winner 不是 best fixed，三个 profile 均有 strict winner，MAPF 单侧 Gate 通过；
- FJSP 预算诊断：同 snapshot 的 CP-SAT 1 s/5 s 在 5/5 cluster 上产生完全相同
  的终态；10 ms 在 5/5 上无可行 artifact，说明预算标签不能替代算法 diversity；
- FJSP 多算法：补齐 DE/PSO 动态残余问题与 stateless artifact 契约后，在 19 个
  有效 cluster 上比较 CP-SAT、DE、PSO；oracle 相对 best fixed 平均降低 24.74
  steps，cluster-bootstrap 95% CI 为 `[12.53, 39.11]`，63.2% cluster 的 winner
  不是 best fixed，三个 profile 均有 strict winner，FJSP 单侧 Gate 通过；
- 联合 profile：在无 loaded transport 的安全 snapshot 上比较 6 个真实 FJSP-MAPF
  组合；20 个 cluster 上 oracle 相对 best fixed 平均降低 19.30 steps，95% CI
  为 `[9.30, 30.85]`，65% cluster 的 winner 不是 best fixed；strict winners
  覆盖 CP-SAT/DE/PSO 和 EECBS/LG-LaCAM/MAPF-LNS2；
